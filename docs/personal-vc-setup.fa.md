# اتصال شخصی VC — راه‌اندازی و تست

این قابلیت جدا از حساب‌های همکاری موجود است. داده خصوصی در Worker و دیتابیس D1 جدا نگهداری می‌شود و از مسیر public bot/monitor مشترک عبور نمی‌کند. کد بات فقط دکمه فرم را در پیوی باز می‌کند. جدول جدیدی به دیتابیس Telegram اضافه نمی‌شود و migrate آن لازم نیست.

## چه چیزی پیاده شده؟

- دستور `/personal` و دکمه «حساب شخصی VC»، بدون نیاز به تأیید همکار.
- فرم اختصاصی با ورود SSO دانشگاه؛ مقدار OAuth state، sesskey و فرم ورود هر بار تازه دریافت می‌شود.
- نگهداری نشست؛ نگهداری رمز فقط با انتخاب صریح checkbox که پیش‌فرض خاموش است.
- رمزنگاری AES-GCM برای رمز، نشست و کش شخصی؛ کلید در Worker Secret جدا از DB. داده به Telegram id احرازشده مقید است.
- امضای Telegram initData، اعتبار ده‌دقیقه‌ای، رد فراخوانی گروهی و عدم پذیرش userId/chatId از ورودی.
- نمایش درس‌ها و فعالیت‌های همان حساب، همگام‌سازی دستی و cron هر نیم‌ساعت برای پایلوت.
- یک تلاش ورود مجدد هنگام انقضای نشست، فقط اگر رمز ذخیره شده باشد؛ خطای شبکه ورود مجدد ایجاد نمی‌کند. هویت دانشگاهی قبل و بعد تمدید باید یکسان باشد.
- اعلان تغییرات فقط به پیوی صاحب حساب. اولین خواندن هر درس، اعلان تاریخی ندارد.
- حذف اتصال و کش شخصی؛ اجرای درحال‌انجام پس از حذف نمی‌تواند داده را دوباره ذخیره کند.

فرم عمومی ورود و مقصد SSO در ۱۶ اکتبر ۲۰۲۶ بررسی شدند. ورود موفق با حساب واقعی در محیط توسعه آزمایش نشده است. تست‌های محلی با پاسخ‌های ساختگی‌اند؛ موفقیت واقعی باید طبق بخش تست تلگرام تأیید شود. کپچا، تغییر قالب SSO یا محدودیت درخواست دانشگاه ممکن است ورود را متوقف کند. در این حالت رمز به دامنه ناشناخته ارسال نمی‌شود.

پیش‌آزمون عمومی خود ماژول جدید نیز روی سایت واقعی موفق بود: دریافت کوکی اولیه VC، دنبال‌کردن redirect و یافتن فرم ورود در دامنه SSO، بدون ارسال هیچ نام کاربری یا رمز.

## مرحله ۱: تست محلی

PowerShell را در پوشه پروژه باز کنید:

```powershell
Set-Location -LiteralPath 'C:\Users\sk138\OneDrive\Desktop\sina\kntu-telegram\KNTU_telegram'
node --test
```

برای تست‌های جدید Node 22.13 یا جدیدتر لازم است؛ Node 24 پیشنهاد می‌شود. تست sqlite ممکن است هشدار Experimental بدهد. این دستور هیچ حساب واقعی را لاگین نمی‌کند و به دانشگاه/تلگرام پیام نمی‌فرستد.

## مرحله ۲: ساخت سرویس شخصی در Cloudflare

Node/npm و حساب Cloudflare لازم است. فرمان‌ها از ریشه همین پروژه اجرا شوند:

```powershell
npx wrangler@4 login
npx wrangler@4 d1 create kntu-personal-vc
```

شناسه database_id برگشتی را در `personal/wrangler.jsonc` جایگزین `REPLACE_WITH_CREATED_DATABASE_ID` کنید. این دیتابیس باید مختص سرویس شخصی باشد؛ دیتابیس عمومی یا production دیگری را به آن وصل نکنید.

```powershell
npx wrangler@4 d1 execute kntu-personal-vc --remote --file personal/schema.sql --config personal/wrangler.jsonc
npx wrangler@4 deploy --config personal/wrangler.jsonc
npx wrangler@4 secret put BOT_TOKEN --config personal/wrangler.jsonc
```

در prompt مخفی، Bot API token همان بات را وارد کنید؛ **توکن مدیریتی TGCLOUD_TOKEN نیست**. مقدار را در فایل، سورس یا چت ننویسید.

کلید تصادفی ۳۲ بایتی تولید و مستقیماً به clipboard منتقل کنید، بدون نمایش آن:

```powershell
$personalVaultBytes = New-Object byte[] 32
[System.Security.Cryptography.RandomNumberGenerator]::Fill($personalVaultBytes)
Set-Clipboard -Value ([Convert]::ToBase64String($personalVaultBytes))
npx wrangler@4 secret put VAULT_KEY --config personal/wrangler.jsonc
```

اگر PowerShell قدیمی شما Fill را ندارد، این جایگزین را استفاده کنید:

```powershell
$personalVaultBytes = New-Object byte[] 32
$personalVaultGenerator = [System.Security.Cryptography.RandomNumberGenerator]::Create()
$personalVaultGenerator.GetBytes($personalVaultBytes)
$personalVaultGenerator.Dispose()
Set-Clipboard -Value ([Convert]::ToBase64String($personalVaultBytes))
npx wrangler@4 secret put VAULT_KEY --config personal/wrangler.jsonc
```

کلید clipboard را در prompt مخفی paste کنید. سپس clipboard را پاک کنید:

```powershell
Set-Clipboard -Value ''
```

کلید را در محل امن مدیر نگهداری کنید؛ تعویض یا گم‌شدن آن، داده‌های رمزنگاری‌شده قبلی را ناخوانا می‌کند. runtime Worker به کلید و رمزگشایی دسترسی دارد؛ این طراحی جداسازی کاربردی و رمزنگاری در ذخیره‌سازی است، نه تضمین عدم دسترسی مدیر زیرساخت.

## مرحله ۳: فعال‌کردن دکمه در بات

پس از deploy، آدرس HTTPS Worker مانند `https://kntu-personal-vc.<your-subdomain>.workers.dev/` چاپ می‌شود. مقدار واقعی همان سرویس را در `tgcloud/lib/config.js` قرار دهید:

```javascript
export const PERSONAL_APP_URL = 'https://kntu-personal-vc.<your-subdomain>.workers.dev/';
```

در صورت خالی‌بودن آدرس، دستور personal فقط پیام «راه‌اندازی نشده» نشان می‌دهد و هیچ فرم دریافت رمزی باز نمی‌شود.

بات را منتشر کنید:

```powershell
npm ci
npx tgcloud push
```

اگر پروژه به بات متصل نیست، ابتدا `npx tgcloud login` را با حساب مدیر انجام دهید. این تغییر schema عمومی ندارد؛ **tgcloud migrate لازم نیست**. کلید دانشگاه را در دستور CLI یا ctx قرار ندهید.

اگر Cloudflare scheduler عمومی قبلی دارید، چون یک ماژول و config بات اضافه شده‌اند، کپی bundle آن را هم طبق راهنمای قبلی redeploy کنید:

```powershell
npx wrangler@4 deploy --config cloudflare/wrangler.jsonc
```

این دستور جایگزین deploy سرویس personal نیست. سرویس personal در deploy خودش فایل‌های UI را از personal/public منتشر می‌کند؛ build جداگانه UI لازم نیست. secrets و دیتابیس هر سرویس مستقل‌اند.

## مرحله ۴: تست در تلگرام

۱. در **پیوی** `@KNTU_aidbot` دستور `/personal` بفرستید. دکمه فرم باید ظاهر شود. همان دستور در گروه نباید دکمه ورود یا داده خصوصی نشان دهد.

۲. فرم را از همان دکمه باز کنید. بازکردن URL در مرورگر معمولی باید به خطای احراز هویت برسد و امکان خواندن یا اتصال حساب ندهد.

۳. نام کاربری و رمز حساب دانشگاهی را وارد کنید؛ checkbox ذخیره رمز را خاموش بگذارید. پس از موفقیت باید درس‌های همان حساب و «تمدید خودکار غیرفعال» نمایش داده شود. رمز پس از ارسال از کادر پاک می‌شود. هیچ رمز یا کوکی نباید در چت ظاهر شود.

۴. یک دقیقه صبر کنید؛ «همگام‌سازی حساب من» را بزنید. فعالیت‌های درس‌ها باید نمایش داده شوند. دریافت نکردن اعلان برای مطالب قدیمی طبیعی است. زمان آخرین همگام‌سازی موفق باید پر شود.

۵. با یک حساب تلگرام دیگر `/personal` را باز کنید. آن حساب نباید اتصال، درس‌ها یا کش حساب اول را ببیند. مسیرهای عمومی مثل /courses نیز نباید با اتصال personal درس جدیدی از آن حساب دریافت کنند.

۶. بدون ذخیره رمز، نشست متعلق به سرویس را از بخش نشست‌های فعال دانشگاه لغو کنید، اگر این امکان وجود دارد. خروج از مرورگر دیگر لزوماً نشست سرویس را باطل نمی‌کند. یک دقیقه بعد همگام‌سازی بزنید؛ باید نیاز به ورود دوباره نمایش داده شود. برای تست، کوکی ساختگی در DB ننویسید.

۷. دوباره متصل شوید و این بار checkbox تمدید خودکار را فعال کنید. بعد از لغو همان نشست سرویس، همگام‌سازی باید یک ورود مجدد انجام دهد و به موفقیت برسد، به شرط پشتیبانی‌شدن جریان واقعی SSO. این مهم‌ترین تست زنده‌ای است که هنوز باید انجام شود.

۸. یک تغییر واقعی و مجاز در یک درس آزمایشی ایجاد شود؛ اجرای بعد باید فقط به پیوی حساب مربوط پیام بدهد. هیچ تغییری در گروه مشترک نباید از این اتصال ایجاد شود. برای آزمایش، تکلیف یا داده رسمی را بی‌دلیل تغییر ندهید.

۹. «قطع اتصال و حذف اطلاعات ورود» را بزنید. وضعیت باید disconnected شود و درس‌ها/فعالیت‌ها ناپدید شوند. همگام‌سازی و cron بعدی نباید حساب را دوباره بسازند. لغو نشست دانشگاه را در خود دانشگاه هم انجام دهید.

## عیب‌یابی

- **سرویس راه‌اندازی نشده:** PERSONAL_APP_URL هنوز خالی است یا بات push نشده.
- **SERVER_CONFIG:** یکی از BOT_TOKEN، VAULT_KEY یا binding دیتابیس تنظیم نشده.
- **UNAUTHORIZED:** BOT_TOKEN با بات بازکننده فرم یکسان نیست، initData منقضی است، صفحه خارج تلگرام باز شده یا Origin نادرست است. فرم را از پیوی دوباره باز کنید.
- **BUSY:** از تلاش قبلی یک دقیقه صبر کنید؛ قفل اجرای طولانی پس از دو دقیقه منقضی می‌شود.
- **LOGIN_FAILED:** ورود SSO قبول نشده یا هویت پس از تمدید ناسازگار است؛ رمز را مستقیم در دانشگاه بررسی کنید.
- **LOGIN_FLOW_UNSUPPORTED:** ساختار یا مقصد ورود با مسیر مشاهده‌شده متفاوت است. متن فرم/کد خطا بدون رمز، کوکی یا URL حاوی اطلاعات موقت برای عیب‌یابی کافی است.
- **DASHBOARD_LAYOUT:** استخراج اطلاعات حساب از داشبورد نیاز به سازگارکردن با HTML فعلی دارد.
- **خطای شبکه:** قطع دسترسی Cloudflare به دانشگاه ممکن است؛ با تغییر رمز حل نمی‌شود. مسیر سرور تا دانشگاه باید جدا بررسی شود.

## حدود این نسخه

این تغییر پایلوت است؛ ۲۰ حساب در هر نوبت نیم‌ساعته و حداکثر ۲۰ اعلان هر کاربر در یک refresh پردازش می‌شود. هنگام رشد صف و زمان‌بندی باید توسعه یابد. تحویل تلگرام و ذخیره رسید تراکنش مشترک ندارند، بنابراین در خرابی بین این دو، تکرار پیام ممکن است. این سرویس نمره، وضعیت تحویل و بهستان را هنوز نمی‌خواند. فایل‌ها و فعالیت‌ها همان محدودیت parser قبلی را دارند. ثبت‌نام قدیمی مبتنی بر نام و اعلان‌های عمومی همچنان مستقل‌اند؛ کاربران برای جلوگیری از اعلان دوگانه می‌توانند اشتراک قدیمی را با /stop متوقف کنند. /forget قدیمی اتصال personal را حذف نمی‌کند؛ حذف personal از فرم خودش است.

دسترسی شخصی به‌صورت خودکار رضایت به اشتراک داده با کلاس/گروه یا حساب‌های همکاری ایجاد نمی‌کند. رمز، نشست و داده رمزگشایی‌شده به لاگ برنامه نوشته نمی‌شوند. از افزودن لاگ بدنه درخواست یا dump دیتابیس در محیط production خودداری کنید.
